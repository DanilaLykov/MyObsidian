
# **AUTH**

сейчас
```json
  auth: {
    isLoading: false,
    isAuthenticated: true,
    deviceToken: null
  }
```

	Как обычно делают: 
	- user → объект текущего пользователя (id, имя, роли, минимум профиля - не нужно тащить все данные)

оптимальный:

```json
auth: {
	accessToken: null,   // при запуске токен из AsyncStorage проверяется, и если не протух - авторизация жива - добавляем в состояние
	user: USER,          // объект текущего пользователя { id, name, roles, ... }
    status:              // статус операций: 'idle' | 'pending' | 'fulfilled' | 'rejected' - идет ли подключение
	    {
			login: 'idle',     
		    logout: 'idle',
		    hydrate: 'pending',   // `hydrate` = «восстановить состояние из сохранённого источника». Достаем токен из async storage и заливаем в состояние
		    refresh: 'idle'
	    }
	error: null          // текст ошибки при логине/логауте - если status === 'rejected' показывать сообщение пользователю
}
```



# **LOADING**

сейчас
```json
loading: {
    isUserLoading: false,
    isChatsLoading: false,
    isChatLoading: false,
    isChatMessagesLoading: false,
    isChatOldMessagesLoading: false
  },
```

Оптимально: не масштабируемо: при росте числа булевых операций список булевых флагов бесконечно разрастается. Мало информации в true/false - показывает только процесс, но не успех/ошибку. Лучшие практики: используют status: 'idle' | 'pending' | 'fulfilled' | 'rejected'. Флаги лучше хранить в соответствующем слайсе, для Chats в Chats, для Messages в Messages.

-  idle` → начальное состояние
- `pending` → операция началась
-  fulfilled` → операция успешно завершена (после завершения состояние сохраняется до следующего вызова) (можно successed)
- `rejected` → ошибка (можно failed)

Вывод: отдельный стэйт **loading** упразднить, и перенести все статусы в соответствующие слайсы.

# **onlineUsers**

	сейчас
	```json
	onlineUsers:
		{
	    '152': {
	      uid: '152',
	      last_online: '2022-04-14 11:34:01'
	    },
	    '153': {
	      uid: '153',
	      last_online: '2018-09-19 11:32:24'
	    },
	    '169': {
	      uid: '169',
	      last_online: '2019-01-16 08:30:15'
	    },
	    '2686': {
	      uid: '2686',
	      last_online: '2025-10-21 11:15:33'
	    }
	  }
	```

В средних проектах для масштабируемости и скорости чтения/обновления если записей тысячи используют немного другую нормализованную структуру. 

оптимально
```json
onlineUsers: {
	byId:
	{      // даёт быстрый доступ к конкретному пользователю по ключу. Это стандарт в документации Redux Toolkit и в большинстве примеров
	    'user_id': { isOnline: true, lastOnline: null },
	    '152': { isOnline: false, lastOnline: '2018-09-19T11:32:24Z' },    // Дата в формате ISO (`YYYY-MM-DDTHH:mm:ssZ`)
	    '210': { isOnline: true, lastOnline: '2019-09-19T11:32:24Z' }    // Дата в формате ISO (`YYYY-MM-DDTHH:mm:ssZ`)
	 },
	allIds: [152, 210]
}
```

Зачем byId:
- Явное разделение между данными и идентификаторами - легче масштабировать, легко добавить рядом другие поля (`status`, `error`, `meta`) без смешивания с данными.
- **Унификация**: совпадает с паттерном нормализации Redux (`byId + allIds`), который используют в средних и больших проектах.
- **Чистота селекторов**: селекторы всегда знают, что данные лежат в `byId`, а не перемешаны с другими ключами.
- **Предсказуемость**: команда сразу понимает, что `byId` — это словарь, а не "смешанный объект".

Здесь status: {} не нужен, т.к. это не отдельный апи-запрос, а вэбсокетное сообщение - это push-событие, а не запрос.

6. **MESSAGES**

сейчас так:
```json
messages: {
    '2': [
      {
        type: 'day',
        date: '2025-08-08'
      },
      [
        {
          id: '3',
          author_uid: '2686',
          text: 'Здравствуйте!',
          created: '2025-08-08 16:50:10',
          chat_id: '2',
          status: '3',
          author_message: {
            '2686': {
              uid: '2686',
              current_user: false,
              name: 'Александр',
              avatar: '',
              avatar_bgcolor: '#ffc107',
              avatar_letter: 'А',
              last_online: '2025-10-21 11:15:33',
              online_user: false
            }
          }
        }
      ],
   
    ],
  },
}
```

Проблема: 
- Смешивание данных и UI‑структуры 
	`type: 'day'` — это чисто UI‑разметка, а не бизнес‑данные. Сообщения хранятся сразу в нормализованном виде, с разделителями по дням и автору. Бэст практис - В стейте хранить только сырые сообщения, а группировку по дням делать селектором (при отображении, на лету).
- Дублирование пользователей - каждый `author_message` повторяет данные (`uid`, `name`, `avatar`, `last_online`). Это ведёт к рассинхронизации: если обновить аватар, придётся менять во всех сообщениях. Нужно убрать author_message в каждом сообщении и хранить только author_uid, а данные автора подтягивать из `users.byId`
- Не нормализовано - сообщения лежат массивами внутри чата. Нет единого словаря `messages.byId`. Сложнее обновлять конкретное сообщение (например, статус доставки).

Оптимально (Best practice для средних проектов)
```json
messages: {
  byId: {
    '3': { id: '3', chatId: '2', authorUid: '2686', text: 'Здравствуйте!', created: '2025-08-08T16:50:10Z', status: '3' },
    '4': { id: '4', chatId: '2', authorUid: '2304', text: 'Добрый день', created: '2025-08-11T09:21:01Z', status: '3' },
    ...
  },
  allIds: ['3', '4', ...],
  status: 
	  {
		fetch: 'idle',       // загрузка сообщений при открытии чата
	    fetchOlder: 'idle',  // подгрузка старых сообщений
	    send: 'idle',        // отправка нового сообщения
	    delete: 'idle',      // удаление сообщения
	    update: 'idle'       // редактирование сообщения
	  },
  error: null
}
```

В средних проектах обычно добавляют отдельный `status` для операций с сообщениями. Это соответствует best practice в средних проектах, где операции с сообщениями независимы.
- **Загрузка списка сообщений** при открытии чата.
- **Подгрузка старых сообщений** при скролле вверх.
- **Отправка нового сообщения** (может быть `pending` → `succeeded` или `failed`).
- Иногда ещё **удаление/редактирование сообщения**.



7. **typing**

сейчас так:
```json
typing: {
    '2': ['2304', '2686'],
    '3': ['153']
}
```

Оптимально так (best practice):
```json
typing: {
  byChatId: {
    '2': ['2304', '2686'],
    '3': ['153']
  }
}

```

**typing** - это отдельный стейт - в **средних/крупных проектах** обычно выносят `typing` в отдельный slice, потому что это временное состояние, не часть бизнес‑логики чата. Если же хранить внутри **chats** - усложняет обновление - при каждом событии typing приходится мутировать chats.byId[chatId] + если чатов много, лишние поля делают slice тяжелее.
Здесь status не нужен, потому что typing не грузится через API, а обновляется в реальном времени. И у него нет долгих операций которые нужно отслеживать, это состояние здесь и сейчас.

**allIds** - здесь избыточен, т.к. allIds нужен только для нормализованных сущностей, где мы храним словарь и хотим быстро итерироваться по всем объектам. В `typing` нет необходимости обходить «все записи» — всегда обращаемся к конкретному `chatId`.
