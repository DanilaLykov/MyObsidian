## **2. placements_weekly**

В этой таблице хранятся данные по неделям, каждой кампании, по каждой площадке - за последние 3 месяца (12 недель).
Этого достаточно, чтобы отлавливать и агрессивных фродеров и "средних/медленных", которые жрут по 100-200 рублей в неделю годами. При этом база данных будет в 20 раз меньше, чем если хранить всю историю. В эту таблицу добавляются не "нулевые" площадки, например если за неделю более 5 кликов.

## **3. placements_blocked**

Здесь строится рейтинг ТОП-1000 площадок по каждой кампании, которые нужно заблокировать.

|                    |         |                                                                                                             |
| ------------------ | ------- | ----------------------------------------------------------------------------------------------------------- |
| campaign_id        | INTEGER | ID кампании                                                                                                 |
| placement_id       | INTEGER | идентификатор площадки                                                                                      |
|                    |         |                                                                                                             |
| danger_score       | REAL    | итоговый рейтинг опасности (пересчитывается каждую неделю)                                                  |
|                    |         |                                                                                                             |
| is_blocked         | INTEGER | 1 = в списке блокировок в Директе, 0 = нет                                                                  |
| first_blocked      | DATE    | дата, когда впервые попала в блок                                                                           |
| last_seen_week     | DATE    | дата последней недели с трафиком. Если площадку давно сняли с ротации в кампании или она умерла, то удаляем |
| manually_unblocked | INTEGER | флаг ручной разблокировки (защита от автоблокировки)                                                        |
|                    |         | PRIMARY KEY (campaign_id, placement_id)                                                                     |
|                    |         | FOREIGN KEY (placement_id) REFERENCES placements_list(placement_id)                                         |
|                    |         | CREATE INDEX idx_blocked_score ON placements_blocked(campaign_id, danger_score DESC);                       |



`last_12w_cost` — сумма нормализированного расхода за 12 недель. Нужна чтобы не пересчитывать каждый раз - это трудозатратно. Просто старую неделю вычел, новую добавил.

`max_week_cost` — максимальный weekly blowup. Чтобы ловить «пиковых» агрессивных фродеров.
Пример:  
```
Площадка А — весь месяц по 200 ₽ 
Площадка Б — за 1 неделю 2500 ₽ → скликивание
```
А суммарно за 12 недель у них может быть одинаково.
Но **опасность у Б существенно выше**, и она должна быть выше в рейтинге.

`rate_per_day_week` — средний «темп» за последние 7 дней. Чтобы быстро поднять вверх свежих фродеров
Пример:
```
если площадка работает 2 дня и уже сожрала 1500 ₽
- rate_per_day = 750 ₽
- normalized → 5250 ₽ за неделю
Даже если она существует всего 2 дня, она отобразится как опасная.
```
Без этого поля **новые фродеры всегда будут недооценены**, что недопустимо.

`first_blocked` - история нужна для двух сценариев:
1. **логирование и аудит**: когда площадка впервые признана опасной
2. **анализ поведения** после разблокировки - если разблокировать площадку → можно смотреть, вернулась ли она в фрод


`last_seen` - критически важно  - показывает когда площадка **последний раз давала трафик**.
- Если площадка "мертвая" 12 недель → можно удалить её из базы
- Если блокировка была 5 недель назад, и она остаётся "мертвой" — отлично
- Если площадку разблокировали и она снова активна — видно сразу

Без этого поля система “захламится”, потому что старые фродеры будут висеть без признаков жизни.



### Пример расчета DANGER SCORE (ИИ)

danger_score = 
    `SUM(cost за последние 12 недель)*1.0`          -- общий вред
  `+ MAX(cost за последние 12 недель)*1.5`         -- пиковая агрессия
`+ (rate_per_day_week * 7)*2`

Пояснение:

- **SUM** → медленные фродеры накопились за 12 недель    
- **MAX** → пик за неделю показывает кратковременный выброс
- **rate_per_day_last_week** → быстрый фрод за последние 1–2 дня

Коэффициенты - чтобы агрессивный фрод за последний день/неделю **имел больше веса**, чем тот, кто жрал 3 месяца по 100₽.

Пример

| Площадка          | SUM(12w) | MAX(12w) | rate_per_day_week*7 | danger_score |
| ----------------- | -------- | -------- | ------------------- | ------------ |
| Старая медленная  | 3000     | 500      | 0                   | 3500         |
| Новая агрессивная | 2000     | 2000     | 5250                | 9250         |

Преимущества

1. **Ловит свежие фродеры** даже за пару дней    
2. **Ловит медленных** через 12 недель суммирования
3. **Отслеживает пики** через MAX
4. **Не нужен total_stolen_micros**, всё решается последними 12 неделями
5. Легко пересчитывать каждую неделю






## Алгоритмы для поиска фродеров (ИИ)

В индустрии анти‑фрода чаще всего используют комбинацию **скоринговых моделей + пороговых правил**:

1. **Rule-based фильтры (пороговые условия)**
    - Простые условия: `CTR > 35%`, `bounce_rate > 60%`, `cost > 200 ₽`.
    - Хорошо ловят очевидных фродеров, но не учитывают динамику.
        
2. **Скоринговая модель (Danger Score)**

![[Pasted image 20251202095443.png]]

Это фактически **взвешенный скоринг**, который позволяет ранжировать площадки и держать топ‑1000.
    

3. **Exponential Decay / Rolling Window**
      Для быстрых фродеров используют экспоненциальное сглаживание: свежие недели имеют больший вес, старые — меньший.   
       Формула:
![[Pasted image 20251202095428.png]]


Так новые всплески сразу поднимают площадку вверх.
    

4. **Anomaly Detection (Z-score, MAD)**    
    - Сравниваешь площадку с её собственной историей или с медианой по кампании.
    - Если `cost` или `CTR` резко выбились из диапазона → сигнал фрода.
    - Это помогает ловить «пиковых» фродеров.
        

👉 На практике: **комбинация скоринга + decay + anomaly detection** даёт лучший результат. Ты можешь хранить danger_score как итоговое число, а алгоритм пересчёта менять без изменения структуры БД.



**ВАРИАНТ ОТ ГРОК**


danger_score = 

    -- 1. Основное наказание за плохое поведение (самое важное при малом трафике!)
    (
          POW(LEAST(bounce_rate, 99.0), 2.1)                          -- 85% → 2200, 95% → 4000, 99% → 5000
        + POW(100.0 / GREATEST(ctr, 0.009), 1.08)                     -- 0.03% → 3500, 0.08% → 1200, 0.20% → 500
        + POW(GREATEST(100 - session_depth * 30, 0), 1.4)            -- 1.0 стр → 1300, 1.3 стр → 800, 2.0+ → 0
        + GREATEST(100 - avg_session_duration_s, 0) * 12.0           -- 15 сек → +1000, 5 сек → +1140
    ) * 800.0

    -- 2. Усиление по деньгам — но ОЧЕНЬ мягкое (чтобы не душить нормальные площадки)
    * (1.0 + total_cost_12w_rub / 3000.0)                           -- 6000 ₽ за 12 нед → ×3, 1500 ₽ → ×1.5

    -- 3. Взлёт новых фродеров — критически важно при малом бюджете!
    + (avg_daily_last_week_rub * 7) * 12.0

    -- 4. Медленные вампиры — тоже ловим, но слабее
    + total_cost_12w_rub * 1.1

## Вариант от чатджпт:

danger_score = 
      0.6 * bounce_component
    + 0.25 * ctr_component
    + 0.15 * slow_fraud_component

`bounce_component = (bounce_rate / 100)^2.2 * 1000`
	это основной маркер качества

`ctr_component = ((campaign_avg_ctr / max(ctr, 0.05%)) - 1) * 150`

- CTR не может давать больше 150–300 штрафа
- но полностью игнорировать CTR — тоже ошибка


`slow_fraud_component = (total_cost_12w_rub / 2000.0) * 120 + max(bounce_trend, 0) * 300 + max(-ctr_trend, 0) * 200`
